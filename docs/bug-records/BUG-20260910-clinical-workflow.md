# BUG-20260910：挂号、检查报告与 AI 会话链路异常

## 现象

- 新增 9 月 14/15 日排班后，数据库和页面显示为 9 月 13 日。
- 页面有排班，AI 查询却返回“暂无医生排班”。
- 挂号确认阶段回复“确认”后，AI 丢失上下文并回到普通问答。
- 普通回复混入“北京协和医院”“官方渠道”“温馨提示”等无关内容。
- 护士挂号后的检查完成事件没有推送给患者，主动解读报告时又提示没有报告。

## 根因

1. 排班日期使用 `java.util.Date`，浏览器、Jackson、JVM 与数据库时区转换造成日期减一天。
2. AI 查询排班时使用同一种日期类型，错误日期和查询参数转换叠加，导致查不到记录。
3. 意图模型先于挂号状态机执行，“确认”会被误判成普通聊天，并清除挂号状态；确认判断又使用子串匹配。
4. 冗长模板来自普通聊天提示词，不是本次 Pinecone 检索结果；当时 Pinecone 实际处于不可用/降级状态。
5. AI 服务重复启动，第二个进程因 8000 端口占用退出，但它创建的 RabbitMQ 消费线程仍取走并确认消息；退出后的线程访问 MongoDB 时出现 `cannot schedule new futures after interpreter shutdown`，造成报告事件丢失。
6. 报告解读只读取 MongoDB 事件缓存，缓存缺失时没有向 HIS 检查结果表回查。

## 修复

- 排班实体、请求对象和响应对象统一改为 `LocalDate`，查询参数按 ISO 日期解析。
- 修复本地数据库中两条已偏移的眼科排班：分别恢复为 2026-09-14 和 2026-09-15 上午。
- 活跃挂号流程优先进入状态机；只有明确切换业务或取消时才退出；确认词改为完整匹配。
- AI 挂号必须选择真实排班，不再绕过号源直接写挂号记录。
- WebSocket 与 HTTP 会话统一加载、保存最近对话；MongoDB 历史按最近 20 条读取后恢复时间顺序。
- 普通聊天限制为短答，禁止虚构医院名称、电话、官方渠道和疫情提示；向量检索过滤明显的爬虫提示文本。
- 增加单实例锁，阻止同一目录重复启动 AI 服务。
- RabbitMQ 消息只在业务处理和幂等标记均成功后 ACK；失败时重新入队；异步数据库操作统一提交给 FastAPI 主事件循环；关闭时等待消费者线程安全退出。
- 报告缓存写入失败会抛错并触发消息重试；主动解读在缓存缺失时从 HIS `/exam_result/patient/{patientId}` 回查最新报告。
- 日志文件按进程号隔离，避免重载/重复进程争用同一日志文件。

## 验证

- Java 相关模块以低内存 Maven 参数编译成功。
- `git diff --check` 无空白错误。
- 本地 MySQL 回查确认两条排班日期已恢复为 2026-09-14、2026-09-15。
- 新增 Python 回归测试，覆盖挂号确认上下文、精确确认词、消息失败不标记、关闭期拒绝消费和单实例锁。

## 复测要求

测试前只保留一个 AI 服务进程，并重启 `RuoYiSystemApplication` 与 AI 服务以加载新代码。检查结果完成后，应同时看到 RabbitMQ 消费日志、MongoDB 报告缓存以及患者会话通知；任一步失败时消息应重新入队，不能被静默确认。
