# 学习记录 - 2026-09-02

## 今日涉及的技术点

### 技术点 1: 超步（SuperStep）—— LangGraph 的最小执行单元

**是什么**：LangGraph 执行图时，不是让节点直接开跑，而是把每次执行拆成一个「超步」。每个超步固定拆成 3 个阶段：

| 阶段 | 干什么 | 关键点 |
|------|--------|--------|
| **① 路由** | 上一个节点执行完后，决定「下一个执行谁」 | 边里写好了判断逻辑；决定串行、并行还是只走某条分支 |
| **② 执行** | 下一个节点的代码开始运行 | 输入来自当前 **state 快照**；执行期间产生的只是**局部更新，暂不提交全局** |
| **③ 提交** | 把节点返回结果合并进全局状态 | 返回内容、日志、当前节点 id 统一写回 state |

记忆钩子：**先问「下一步去哪」（路由）→ 再「干活」（执行，只动局部）→ 最后「交作业」（提交，写回全局 state）**。

**为什么要有路由**：初学的图太简单（两个节点一条线）。真实工程里图可能有一两百个节点，节点间不是简单串联，需要路由阶段内部做选择判断——一个节点指向两个出口时，有判断就只执行一个，没判断就可能并行执行。

**例外：开头和结尾**
- 开头：从 `start` 直接进入第一个节点，前面没有「路由」
- 结尾：节点标记 `end` 后直接运行完，图就结束
- 只有中间节点之间，才完整经历「路由 → 执行 → 提交」

**用在哪里**：本项目有两张图，正好是这套模型的完整标本：

| 图 | 位置 | 结构 |
|---|---|---|
| 父图（诊断工作流） | `nodes.py:555` `create_diagnosis_graph()` | 10 节点星型：1 入口 → 9 选 1 → 汇总 → END |
| 子图（ReAct 循环） | `react_agent.py:190` `build_react_agent()` | 2 节点环形：agent ⇄ tools |

### 技术点 2: 路由阶段的实现 —— 条件边 + 路由函数

**是什么**：`add_conditional_edges(源节点, 路由函数, {返回值: 目标节点})`。路由函数读 state 快照，返回一个字符串决定下一个节点。

**用在哪里**：父图 `route_intent`（`nodes.py:528-552`）：

```python
def route_intent(state: GraphState) -> str:
    intent = state.get('intent')
    event_type = state.get('event_type')

    # 事件驱动的路由（优先级更高）
    if event_type == "examination_ordered":
        return "examination_event"
    elif event_type == "report_generated":
        return "report_event"
    elif event_type == "prescription_created":
        return "prescription_event"

    if intent == IntentType.TRIAGE:
        return "triage"
    # ...
    else:
        return "response_generation"
```

注册处（`nodes.py:576-590`）把 9 个返回值映射到 9 个节点。

**关键发现**：
- 这是**有判断就只执行一个**的典型——9 个出口，每个超步只走 1 条，全串行无并行。
- `event_type` 优先级高于 `intent`：RabbitMQ 事件驱动的请求会绕过意图分支，直接进 3 个 event 节点。

**子图的路由更典型（二选一 + 回环）**，`react_agent.py:171-202`：

```python
def should_continue(state: ReActState) -> str:
    last_msg = state["messages"][-1]
    if isinstance(last_msg, AIMessage):
        fc = last_msg.additional_kwargs.get("function_call")
        if fc and fc.get("name"):
            if iter_count >= max_iterations:
                return "end"      # 硬兜底
            return "tools"
    return "end"

workflow.set_entry_point("agent")
workflow.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
workflow.add_edge("tools", "agent")   # 无条件边，永远回 agent
```

`add_edge("tools", "agent")` 是无条件边——tools 干完活永远回 agent，**然后再由 `should_continue` 路由一次**。所以一个完整 ReAct 回合 = 2 个超步：`agent→(路由)→tools` 和 `tools→agent`。

### 技术点 3: 执行阶段 —— state 快照 与 局部更新的隔离

**是什么**：节点从全局 state 快照读输入，产生的更新在被提交前不进入全局。

**用在哪里**：全局快照即 `GraphState`（`nodes.py:9-26`），节点内全是 `state['messages'][-1].content`、`state.get('patient_id')` 这类读法。

**最直观的「局部更新不提交全局」例子** —— 子图跑在自己的 `ReActState` 上，父图全程看不见（`nodes.py:147-160`）：

```python
graph = build_react_agent(tools, system_prompt, max_iterations=4, temperature=0.3)

result = await loop.run_in_executor(
    None,
    lambda: graph.invoke({
        "messages": [HumanMessage(content=user_message)],
        "iteration_count": 0,
    })
)

parsed = parse_json_result(result)
state["triage_result"] = parsed      # ← 只有这一行才提交回父图全局
```

子图内部跑了多少轮 ReAct、messages 堆了多少条，都是子图局部状态；只有 `state["triage_result"] = parsed` 才算「交作业」。

### 技术点 4: 提交阶段 —— reducer 决定「怎么合并」

**是什么**：节点返回的内容如何并入全局，由 state 字段上声明的 **reducer** 决定。没声明 reducer 的字段，LangGraph 默认行为是**覆盖**。

**关键发现一：本项目父图绕过了「只提交增量」的设计**。

父图所有节点都是 `return state`（返回全量），例如 `nodes.py:67-75`：

```python
    log.info(f"意图识别完成 - intent: {state['intent']}, confidence: {state['confidence']}")

except Exception as e:
    state['error'] = f"意图识别失败: {str(e)}"
    state['intent'] = IntentType.CHAT

return state     # ← 返回整个 state，不是局部增量
```

因为 `GraphState` 里**没有任何字段用 `Annotated[...]` 声明 reducer**，默认 reducer 是覆盖，所以效果等于全量写回——语义正确，但不是教材讲的「局部更新合并」那条路子。

**关键发现二：唯一用标准合并语义的是子图的 `messages`**（`react_agent.py:39-42`）：

```python
class ReActState(TypedDict):
    messages: Annotated[List[BaseMessage], add_messages]
    iteration_count: int
```

`add_messages` 是追加式 reducer（按 message id 做 upsert，不重复追加）。配上下面的局部返回（`react_agent.py:130-133`），才是教材讲的规范写法：

```python
return {
    "messages": [response],
    "iteration_count": iter_count + 1,
}
```

> **结论**：要学「提交」的规范写法，看 `react_agent.py`（子图），别看 `nodes.py`（父图）。

### 技术点 5: 开头 / 结尾的例外

**是什么**：entry 前无边，END 后无边，不参与完整的超步三段式。

**用在哪里**：
- 开头无路由：`workflow.set_entry_point("intent_recognition")`（`nodes.py:573`）、`set_entry_point("agent")`（`react_agent.py:196`）
- 结尾无后续路由：`workflow.add_edge("response_generation", END)`（`nodes.py:603`）

**细微差别**：父图的 END 是**固定边**；子图的 END 是**路由函数的返回值**（映射在 `{"end": END}` 里），属于条件边的一种出口。

### 技术点 6: 超步不能无限跑 —— 循环图的收敛控制

**是什么**：教材没提但工程必配。环形图必须有退出条件，否则无限循环。

**用在哪里**：项目用 `max_iterations` 自控，做了**软着陆 + 硬兜底**两层（分诊默认 4 轮）：

软着陆 —— 最后一轮注入提示让 LLM 主动收敛（`react_agent.py:110-117`）：

```python
if iter_count >= max_iterations - 1:
    full_messages = list(full_messages) + [
        SystemMessage(content=(
            "这是最后一轮，你没有更多工具调用次数了。"
            "请立即基于已有信息生成最终JSON结果回复患者，不要再调用任何工具。"
            "即使某些信息不完整，也必须给出你的最佳判断。"
        ))
    ]
```

硬兜底 —— 路由函数直接掐断（`react_agent.py:183-186`）：

```python
if iter_count >= max_iterations:
    log.warning(f"[ReAct] 达到最大迭代 {max_iterations}，强制结束")
    return "end"
```

项目未设 `recursion_limit`，用的是 LangGraph 默认 25。

### 技术点 7: 用 SSE 实时观察超步

**是什么**：`astream()` 吐出的每个 chunk 就是**一个超步执行完后的 state 快照**，dict 的 key 是节点名。

**用在哪里**：`app/api/v1/chat.py:57-65`：

```python
async for chunk in workflow.run_stream(initial_state):
    node_name, node_state = list(chunk.items())[0]
    if node_name not in STATUS_MAP:
        continue

    yield _sse_event("status", {
        "step": node_name,
        "message": STATUS_MAP.get(node_name, f"执行中: {node_name}"),
    })
```

前端每收到一个 `status` 事件，就对应一次「路由→执行→提交」的完成。这是调试超步最直接的手段。

> 对比：`ainvoke()`（`workflow.py:39`）只返回终态，看不到中间超步。

### 技术点 8: Checkpoint —— 本项目尚未使用

**是什么**：视频里的比喻是「有个摄影师在不同位置给你拍照，记录当前状态」，本质是**状态的持久化保存**。本集只埋伏笔，未展开。

**关键发现**：全仓搜索 `checkpointer` / `MemorySaver` / `SqliteSaver` / `thread_id` / `configurable` / `get_state` / `update_state` / `recursion_limit`，**零命中**。两处 compile 都是裸调用：

```python
# workflow.py:19
self.graph = workflow.compile()

# react_agent.py:204
compiled = workflow.compile()
```

跨轮次对话记忆是项目**自己用 Agent 层实现**的（`triage_agent._load_memory` 见 `nodes.py:99`，`triage_agent.remember` 见 `nodes.py:164`，底层是 MongoDB），跟 LangGraph 的 checkpoint 是**两套独立的东西**。

### 技术点 9: GraphState 17 个字段的实战解读

**是什么**：父图状态 `GraphState`（`nodes.py:9-26`）是一张**会诊流转单**——所有节点读写同一份，每个节点领到后填几栏再传给下一个，最终患者看到 `response` 那一栏。17 个字段按用途分 6 组：身份标识 / 输入 / 路由决策 / 业务结果 / 事件入口 / 输出异常。

**关键发现**：
- **业务结果 5 个字段一次请求只填 1 个**，其余全程 `None`（图是星型，9 分支只走 1 条），它们本质是预留槽位
- **`event_type` 优先级高于 `intent`**：RabbitMQ 事件请求会绕过意图分支，走独立于用户对话的入口
- **`error` 不会中断流程**：节点 catch 异常后只写入 `error`，后续节点照常执行
- **`TypedDict` 运行时就是普通 dict**：不校验类型、不设默认值、无 reducer，全靠 `chat.py:41-50` 的 `initial_state` 显式初始化

## 踩到的坑

本次为纯代码走读，未触发运行时问题。但走读中发现两处**容易误读代码**的地方：

* **坑 1：以为父图节点返回的是「局部增量」**
  * 现象：看到 `return state` 会误以为 LangGraph 会把整个 state 当增量合并
  * 原因：`GraphState` 无 reducer 声明，默认覆盖语义，所以全量返回恰好能work，但语义上绕过了框架设计
  * 影响：并发写同一字段时无保护；想改成增量提交需要先给字段加 `Annotated[..., reducer]`

* **坑 2：以为 checkpoint 已经在用了**
  * 现象：对话确实有「记忆」，容易被当成 LangGraph checkpoint 的功劳
  * 原因：记忆来自 `TriageAgent`/`ReportAgent` 自己读写 MongoDB，与 LangGraph 无关
  * 影响：不能依赖 `get_state()`/`update_state()` 做时间旅行，也不能靠 `thread_id` 恢复中断的图
