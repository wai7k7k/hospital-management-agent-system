# 学习记录 - 2026-06-09

## 今日涉及的技术点

### 技术点 1: Spring MVC 日期参数绑定双通道

**是什么**：Spring 处理日期参数有两套独立的转换机制：
- `@DateTimeFormat` → Query String / 表单字段的参数绑定
- `@JsonFormat` → JSON body 的 Jackson 反序列化

**用在哪里**：`RegisterBo.registerDate` 缺了 `@DateTimeFormat`，导致 `?registerDate=2026-06-09` 无法转为 `java.util.Date`。

**关键知识点**：两者不能互换。前端 GET 请求传日期参数必须加 `@DateTimeFormat`，POST JSON body 才用 `@JsonFormat`。

### 技术点 2: MyBatis-Plus BaseMapper 的 VO 自动映射

**是什么**：`baseMapper.selectVoPage()` / `selectVoList()` 不经过 XML `<resultMap>`，直接用字段名→列名的驼峰转换做映射。所以 DB 的 `dep_name` 列可以直接映射到 VO 的 `depName` 字段，不需要额外配置。

**踩坑**：`queryPageList()` 在查询后用 `sys_dept` 的 ID→Name 映射覆盖 VO 值。`dep` 表和 `sys_dept` 表的 ID 不重合，覆盖成了 null。

### 技术点 3: 双写入路径的一致性陷阱

**是什么**：同一个业务操作（创建挂号记录）有两条代码路径：
- 人工挂号：`GuahaoController → GuahaoServiceImpl.guahao()`，写 DB + 写 Redis + 扣排班名额
- AI 挂号：`RegisterController → RegisterServiceImpl.insertByBo()`，写 DB + 发 RabbitMQ 事件

**关键发现**：AI 路径漏了 Redis 写入，导致 `getRegisterByCardId`（只查 Redis）永远找不到 AI 挂号单。

### 技术点 4: EARS 需求澄清方法

**是什么**：EARS (Easy Approach to Requirements Syntax) 是一套需求书写规范，把需求分为 5 种类型（普遍型 Ubiquitous / 事件驱动型 Event-driven / 非期望行为型 Unwanted / 状态驱动型 State-driven / 可选特性型 Optional）。

**实践**：把用户 4 个 bug 描述用 EARS 格式重新整理后发现——事件驱动型和普遍型需求最需要验收标准；非期望行为型需求必须写明"什么不应当发生 + 发生后的处理方式"。
