# 学习记录 - 2026-06-09 (续)

## 今日涉及的技术点（第二轮修改）

### 技术点 1: 就诊页身份证查询的双层架构

**是什么**：`getRegisterByCardId` 先查 Redis 缓存，未命中时再查 DB。这是一个典型的 cache-aside 模式。

**踩坑**：人工挂号路径写 Redis，AI 挂号路径只写 DB 不写 Redis。cache-aside 的前提是"所有写入路径都更新缓存"，漏一条就导致缓存穿透。

**修法**：`RegisterServiceImpl.insertByBo` 补写 Redis；`getRegisterByCardId` 增加 DB 兜底查询。

### 技术点 2: ResultVO 和 R<T> 的差异

**是什么**：
- `R<T>`：`{"code":200, "msg":"...", "data":{...}}`
- `ResultVO`：`{"code":200, "message":"...", "data":{...}}`

**踩坑**：`_parse_response` 只返回 `data` 字段的内容。`do_guahao()` 返回的 `ResultVO` 里关键信息（`message: "ok"`）在顶层不在 `data` 里，被 `_parse_response` 吃掉了。

**修法**：`do_guahao()` 直接读 `response.json()` 取完整对象。

### 技术点 3: @DubboReference 的 IDEA 误报

**是什么**：IDEA 的 Spring 自动装配检测不认识 `@DubboReference`（Dubbo 的注解），所以报 "Could not autowire"。运行时 Dubbo 通过 Nacos 注册中心动态发现服务，注入能正常工作。

**用在哪里**：`RegisterServiceImpl` 的 `RemotePatientService`、`RemoteUserService`、`RemoteDeptService` 三个 Dubbo 字段，IDEA 报红但编译和运行都正常，不需要加 `@Autowired`。

### 技术点 4: 双路径对齐原则

**是什么**：同一个业务操作有多条代码路径时（人工 vs AI），每条路径必须产生相同的副作用（DB 写入 + Redis 缓存 + 事件发布）。

**为什么要关注**：这次 AI 挂号漏写 Redis 是最典型的例子。以后遇到"某个功能 A 方式可用、B 方式不可用"，第一反应就是去对比两条路径的副作用差异。
